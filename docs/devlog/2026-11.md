# Development log — November 2026

## 2026-11-04 — The app API's types and checks

**Done:** [ADR-0004](../decisions/0004-talking-to-the-cloud.md), and its first step: the app API's types and checks, made from ai-platform's schema. `platform/` moves to `app/v1.2`.
- **`npm run protocols`** writes them into `src/shared/protocols/generated/`: json-schema-to-typescript's types for every definition, and Ajv's standalone checks for the 15 bodies that the schema's `from_cloud` tells apart. CI runs it with `--check`, and fails if what is committed differs.
- **`received(definition, body)`**, in `shared/protocols`, gives a body as its type, or a `ProtocolError` that says where and which rule, never the value.
- **Tests:**
  - every body that ai-platform's examples have the cloud send passes;
  - the generated checks give the same verdict as Ajv compiling the schema in the test, on those bodies and on bodies planted to break its patterns and conditions;
  - three mutants of the checks all failed them.

**Decisions:** The owner left the choices of this work to the assistant, to be made for long-term development (ai-platform's dev log, 2026-11-03). ADR-0004 records them:
- checks compiled before the app runs, since Hermes does not promise the Function constructor;
- one client over a transport that is a port, with a simulated cloud;
- the refresh token in expo-secure-store, the access token in memory;
- the simulated cloud by default, and a real one named only on the machine that builds.

**Problems / unfinished:** Ajv's strict mode refuses a `then` that requires a property its parent declares, as the app API's member does, though JSON Schema allows it. The generator turns that one rule off.

**Next:** `shared/cloud`, the simulated cloud, and `account`, signing in with the development provider. Then `homes`.

## 2026-11-04 — The app API's client, and the simulated cloud

**Done:** `shared/cloud`, ADR-0004's second step.
- **The client**, over a transport that is a port:
  - `SignInClient` asks for nonces, exchanges ID tokens, refreshes, signs out, and asks the development provider for ID tokens;
  - `CloudClient` reaches the account, its sessions, homes, their people and invitations;
  - it sends the access token, renews it once on 401 through `Credentials`, which `account`'s session will be, sends `If-Match` and walks pages;
  - each refusal becomes an error that names the operation and what happened, never a value;
  - a request with an Idempotency-Key is sent again with that key when no answer came, or when its first copy still runs (409), up to `retries` times, each wait twice the last.
- **The fetch transport:** a time limit, a limit on an answer's size (SEC-15), and no cookies.
- **The simulated cloud:** the app API 1.2 in memory, as ai-cloud serves it, with its checks in its order and its settings' values. Simulated Google and Apple sign people in for the tests. It answers after `latency`, so that screens wait as for a real cloud.
- **The configuration's `[cloud]`:** the simulated cloud by default; a cloud's address from `config/local.toml` or `AI_APP_CLOUD_ADDRESS`, and `http://` only in development (SEC-1).
- **A check for every definition** ([ADR-0005](../decisions/0005-checks-for-every-definition.md)), and arrays for the types of lists.
- **Tests:**
  - ai-platform's four examples replay against the simulated cloud, through its transport, as against ai-cloud;
  - the client runs end to end on it, and the fetch transport against a stand-in for fetch;
  - the rules that the examples leave out: limits, lifetimes, what deleting takes;
  - 27 mutants of the client and the simulated cloud. One survived at first: a test of a fresh sign-in's age passed because its nonce had expired too, and now isolates that rule.

**Decisions:** delegated, as in the entry before.
- ADR-0005: a check for every definition.
- The rest of the way splits in three: this step; then `account`, with the session, signing in and its screens; then `homes`.
- The client sends again only what an Idempotency-Key makes safe. TanStack Query retries the queries, and no mutation by default ([its guide](https://tanstack.com/query/latest/docs/framework/react/guides/mutations), read 2026-11-04).
- The simulated cloud asks the JavaScript engine for time zones: in Node, ICU; on a phone, the platform's own, which [Hermes's Intl](https://github.com/facebook/hermes/blob/main/doc/IntlAPIs.md) uses. ai-cloud reads tzdata's list.

**Problems / unfinished:**
- Met and solved: the builds failed in CI, where Expo reads the configuration. smol-toml makes tables without a prototype, which Expo's reader cannot serialize, and the runtime settings now carry the `[cloud]` table. The loader makes them ordinary objects, and a test reads the configuration through Expo's own `getConfig`.
- A refresh whose answer is lost ends the session: the cloud has rotated the token, and the next refresh presents the old one, which counts as stolen (RFC 9700, 4.14.2). Large providers allow a grace period for this, read 2026-11-04:
  - Okta's "grace period for token rotation": 30 seconds by default, from 0 to 60 ([guide](https://developer.okta.com/docs/guides/refresh-tokens/main/));
  - Auth0's "reuse interval": off by default, and only for the token just replaced ([docs](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation)).

  To settle in ai-platform before `account`'s session.
- Since Android 9 (API level 28), Android refuses plain HTTP unless the app's network security configuration permits it, for an address or for all ([Android's documentation](https://developer.android.com/privacy-and-security/security-config), read 2026-11-04). A developer's own cloud over `http://` needs that permission, for its address only, which comes with `account`.

**Next:** `account`: the session in secure storage, signing in with the development provider, and its screens; TanStack Query at the root.

## 2026-11-04 — Signing in, and the session

**Done:** the `account` module, and the app API 1.3, whose refresh may be sent again after a lost answer ([ai-platform ADR-0011](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0011-refreshing-again.md)).
- **The session** is the cloud client's credentials:
  - its refresh token is in secure storage, under a name of the cloud's own; its access token is only in memory;
  - one refresh at a time, whoever asks, `refresh_margin` before the token expires;
  - a refresh is sent again at once when no answer came;
  - `invalid_grant` ends the session, the sign-in screen says so, and the cache forgets the person's data;
  - signing out ends it here at once, then at the cloud if it can be reached;
  - work begun before a sign-in or a sign-out changes nothing after it, and a request made while the session is restored waits for it.
- **Signing in** with the development provider: a test person, by name and email, checked with the app API's own patterns before anything is sent. The providers the screen offers are a setting.
- **The account screen:** the person's name and email, and signing out. The homes' header leads to it with a disc of the name's first letter, as Google's apps show an account without a picture.
- **The routes:** the homes and the account once signed in, signing in until then, with Expo Router's protected routes. The splash screen stays until the session is known.
- **`shared/queries`:** TanStack Query, which tries a read again only after no answer or a cloud that cannot serve, and follows the app's focus and the phone's network.
- **The design system:** `TextField`, with its label above it and help or a fault below it, and danger's colours, worked out from a red as the tone's are. The studio shows both.
- **The simulated cloud** keeps to the app API 1.3, and `sign-in.json`'s retry replays against it.
- **Tests:**
  - the session against the simulated cloud: restoring, refreshing, the lost answer, the cloud ending the session, signing out with or without a cloud, the race of a refresh with a sign-out, storage that refuses;
  - the screens, the routes, the text field, the cache;
  - 9 mutants of the session and the simulated cloud. One survived at first: the race test held the request, not its answer, so the refresh was refused and never kept.

**Decisions:** delegated, as before.
- iOS keeps the refresh token `WHEN_UNLOCKED_THIS_DEVICE_ONLY`: a session is one app on one phone, and the app refreshes only while it is used. A background refresh would need `AFTER_FIRST_UNLOCK`.
- On the simulated cloud, the session lives in memory: that cloud forgets its sessions when the app stops, and a kept token would only end in "your session has ended".
- The session label is the phone's model, not its name, which people set and which may name them (expo-device).
- The account's disc is a link, as Expo Router's `Link` makes it: it leads to another screen.

**Problems / unfinished:**
- Met and solved: React Native Testing Library 14's events must be awaited, and Expo Router's header is native, which Jest does not draw.
- A development build reaching a developer's own cloud over `http://` still needs Android's network security setting and iOS's App Transport Security exception for that address. Expo Go reaches one already. It is a step of its own, once each platform's rules for addresses are read.

**Next:** `homes`: the list, creating a home, its people, profiles and invitations.

## 2026-11-04 — Homes: the main screen, and a new home

**Done:** the first of `homes`.
- **The main screen is one home,** as in Google's Home: its name, the person's role there, and the people in it. The person's other homes are a step away (`/homes`), and so is a new one (`/homes/new`). Each home has an address, `/homes/<id>`, that a link or a notification can open.
- **With no home,** a new owner is welcomed under the robot's light, and offered to create one.
- **A new home:** its name starts as the person's own home, "Linh's home"; its time zone and languages are the phone's, which its robots keep until told otherwise. An account in as many homes as it may be is told so.
- **`shared/cloud`:** `everyPage`, which reads a list whole and stops on a page token given twice; the failures' messages, moved there from `account`.
- **The catalogs:** `plainText`, without MF2's isolating marks, for text that becomes data. The default name would otherwise have stored two invisible characters, U+2068 and U+2069, in the home's name: they are not control characters, so the name's pattern lets them through.
- **Tests:** the welcome, a home and its people, more than one home, the defaults and the limit, and the whole way from signing in to a new home. A mutant that puts the marks back fails them.

**Decisions:** delegated, as before.
- Which home the main screen shows lasts while the app runs: the first, or the one opened. Remembering it across starts needs storage for preferences, which comes with the settings.
- Languages show as their tags. Hermes has no `Intl.DisplayNames` (its IntlAPIs.md lists Collator, NumberFormat, DateTimeFormat and getCanonicalLocales), so their names will come from the catalogs, with the languages' settings.

**Problems / unfinished:**
- Bidirectional controls in a name (U+202A to U+202E, U+2066 to U+2069) can make one name look like another. The app API's name pattern refuses control characters only. Whether names should refuse those marks too is a question for ai-platform.
- Invitations, profiles, roles, leaving, handing a home over and deleting it come next. Handing over and deleting need a fresh sign-in, which the development provider can give with the person's own name and email.

**Next:** the people of a home: profiles, invitations and joining, roles, leaving.

## 2026-11-04 — Invitations, profiles, and joining a home

**Done:** the people of a home, but for roles, leaving and removing ([ai-platform ADR-0009](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0009-people-in-a-home.md)).
- **Inviting someone:** the owner and admins make a link that works once: the cloud's address, `/join#`, and the code. It is shared through the phone's own sheet, or copied from the screen. It shows only there, since the cloud keeps the code's hash: the cache forgets it with the screen.
- **The invitations not yet used** show under the people, with who made each and when it expires, to revoke.
- **Profiles:** the owner and admins add a person who never signs in, by name.
- **Joining:** `/join` opens with a link's code, or takes a pasted link or code. A person signed out signs in on that screen, so the link keeps its place. Then they see the home and who invited them, and agree. A code that cannot be used is said so, with no reason, since the cloud gives none.
- **The catalogs** format dates with MF2's `:datetime` (`DraftFunctions`), in the phone's own locale for the language: an `en` message shows a British phone's dates.
- **Routes:** every guard names where it leads. Without one, Expo Router leads to the first open route by name, which made `/join` the start of every person signed out.
- **Tests:** the screens, the whole way from a link to the home it opens, and the code leaving the cache with its screen. The tests run in UTC, and the simulated cloud takes a clock, so that an expiry reads the same everywhere.

**Decisions:** delegated, as before.
- A link is made by a tap on its own screen, after what it allows is said, as Telegram makes a new link. One made as the screen opens would be made twice in development, by React's Strict Mode, and each counts towards the home's open invitations.
- Revoking takes no confirmation, as Discord's invites: a new link is a tap away.
- Signing in from a link happens on the link's own screen: Expo Router's guards replace the screen they leave, and the link would be lost.

**Problems / unfinished:**
- Hermes has no `Intl.PluralRules` (its IntlAPIs.md, read 2026-11-04), which MF2 needs to choose a plural. No message has one yet; the first needs a polyfill, which FormatJS's guide for React Native names.
- The QR code: showing a link as one, and the app's own scanner. Until the project has a domain, they and a pasted link are the ways to join (ADR-0009).
- Opening the app from a link needs that domain, for Android's App Links and Apple's universal links.

**Next:** the QR code, then roles, renaming, removing and leaving.

## 2026-11-04 — The invitation's QR code, and the app's scanner

**Done:** the way to join in person, and the way a link reaches the app until the project has a domain (ai-platform ADR-0009).
- **The link's QR code** shows when the link is made, above the button that shares it. The design system's `QrCode` draws it with Skia, dark on light in both themes, with the four-module margin that DENSO WAVE asks for, and each module a whole number of pixels.
- **`shared/scanner`** reads QR codes with expo-camera, for `homes` now and `setup` later. It says why before the phone asks, leads to the settings once the phone may not ask again, reads the permission again when the person comes back from them, and reads QR codes alone, each refused one once.
- **Joining** offers the scanner first, and the field for a pasted link under it.
- **The camera's permission:** no microphone on either platform. iOS's reason comes from the catalogs, in each language, through Expo's `locales`, which takes objects as well as files.
- **Tests:** the code drawn back into pixels reads as the link, with its quiet zone clear; the colours; the scanner's permission and its codes; joining by scanning; the configuration a build reads.

**Decisions:** delegated, as before.
- **The encoder** is Paul Miller's `qr` 0.7.2 (2026-09-28, MIT or Apache-2.0, no dependencies), which tests its codes against python-qrcode, and whose decoder lets the tests read the drawn code back. Compared on npm, 2026-11-04:
  - `uqr` 0.1.3 (2026-04-03), from Nayuki's generator, encodes only;
  - `qrcode-generator` 2.0.4 (2025-08-07);
  - `qrcode` 1.5.4 (2024-08-05) brings `pngjs` and `yargs`, and no types.

  `qr` uses `TextEncoder`, which Hermes has (its Features.md, read 2026-11-04).
- **The QR code is dark on light** in the dark theme too: ZXing tries the inverted image only when asked (`DecodeHintType.ALSO_INVERTED`).
- **The scanner** is expo-camera's own, which Expo Go has: no second camera library.

**Problems / unfinished:**

- The Android manifest that `npx expo config --type introspect` shows also asks for storage, and to draw over other apps. Where they come from, and whether a release needs them, is to check before the first release.

## 2026-11-05 — Roles: the owner makes a person an admin or a member

**Done:** roles, on the person's page ([ai-platform ADR-0009](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0009-people-in-a-home.md); the app API, Changing a person).
- **The role** shows to the owner alone, on another person's page, between the name and removing: Admin or Member, each with a line on what it allows. Never for the owner themself, nor for a profile (`maySetRole`).
- **Choosing** sends the role at once, with `If-Match`. While the cloud is asked, the choice shows the role chosen, the tone pulses beside its label, and the name waits, since both changes carry the same ETag. A refusal returns the choice to the role the cloud has, and says why; a change made meanwhile is said so, to choose again.
- **Demoting an admin** revokes the invitations they made: the open ones are read again, whatever the answer, and the page says "Invitations from An not yet used are revoked."
- **The design system:** `ChoiceList`, one of a few options, each with a line on what it means, marked as each platform marks a choice (`MARK`). The studio's components page shows one to choose, made busy by the button that starts and stops waiting, and one not available.
- **Tests:** the component on both platforms, busy, disabled and with reduce motion, and its checkmark's geometry; who is offered a role; promoting and demoting on the simulated cloud; the page while the cloud is asked; a change made meanwhile; the home's invitations read again after a demotion, and not after a promotion; a removal that the role no longer allows. 56 mutants, all killed. One survived at first: the owner's own role, which the owner check refused too. A page read while the caches disagree, after a hand-over, now isolates it.

**Decisions:** delegated, as before. Sources read 2026-11-05.
- **The control's shape follows each platform:**
  - Android: "Use radio buttons when the user needs to see all available options" ([Material Components for Android](https://github.com/material-components/material-components-android/blob/master/docs/components/RadioButton.md)). The whole row is the target, the radio button leading it, with `selectableGroup` and `Role.RadioButton` ([Compose's radio button](https://developer.android.com/develop/ui/compose/components/radio-button)). The mark's sizes are Compose's Material 3 `RadioButton`'s: 20, a 2 ring, a 12 dot.
  - Apple: radio buttons are macOS's alone ([HIG, Toggles](https://developer.apple.com/design/human-interface-guidelines/toggles)). On iOS, "a table that lists options often highlights a row only briefly before adding an image — such as a checkmark — indicating that the item is selected" ([HIG, Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)).
  - React Native Paper draws its radio button the same way, by platform: a circle, or on iOS a checkmark ([`RadioButton.tsx`](https://github.com/callstack/react-native-paper/blob/main/src/components/RadioButton/RadioButton.tsx)).
- **Screen readers,** in React Native 0.88's source: on Android, a `radio` is an `android.widget.RadioButton`, checked or not (`ReactAccessibilityDelegate.kt`). iOS has no radio trait, so React Native puts "radio button, checked" in the element's value, from strings it ships in Vietnamese too (`RCTViewComponentView.mm`). The line on what an option means is its hint, as a field's help is, so that its name stays its label, which people say to choose it.
- **A choice commits at once,** as lists of options do on both platforms, with no dialog: a role can be given back in a tap. The invitations a demotion revokes are no reason to ask, since the app revokes invitations without asking: a new link is a tap away.
- **After a demotion,** the page says that the admin's invitations not yet used are revoked. It cannot say which: an invitation names its maker by a name, which can change or repeat.
- **One haptic for one touch:** `select` as the choice moves, `error` if the cloud refuses, and no `success`, which would answer the same touch twice.
- **The checkmark is drawn with views,** two bars with round ends, so that it blends with the tone as the rest does (`VIEW_BLEND`). Skia would need a blend of its own, as `Glow` has.

**Problems / unfinished:**
- `accessibilityRole="alert"` announces nothing on iOS: React Native gives it no trait, and only `AccessibilityInfo.announceForAccessibility` posts an announcement (`RCTViewManager.m`, `RCTAccessibilityManager.mm`). So every screen's failures, and the note after a demotion, are silent on iOS until a screen reader reaches them. The fix belongs to the design system, for every screen at once: an alert that announces itself as it comes, tried with VoiceOver and TalkBack.
- Not seen on a phone yet: the marks, the busy choice, and what screen readers say of them.
- A test file run alone still never exits: the handle of 2026-11-04 is still open. Mutants' runs pass `--forceExit`.

**Next:** handing a home over and deleting it, with a fresh sign-in.
