## 2026-11-04 — The app API's client, and the simulated cloud

**Done:** `shared/cloud`, ADR-0004's second step.
- **The client**, over a transport that is a port:
  - `SignInClient` asks for nonces, exchanges ID tokens, refreshes, signs out, and asks the development provider for ID tokens;
  - `CloudClient` reaches the account, its sessions, homes, their people and invitations;
  - it sends the access token, renews it once on 401 through `Credentials`, which `account`'s session will be, sends `If-Match` and walks pages;
  - each refusal becomes an error that names the operation and what happened, never a value;
  - a request with an Idempotency-Key is sent again with that key when no answer came, or when its first copy still runs (409), up to `retries` times, each wait twice the last.
- **The fetch transport:** a time limit, a limit on an answer's size (SEC-15), and no cookies.
- **The simulated cloud:** the app API 1.2 in memory, as ai-cloud serves it, with its checks in its order and its settings' values. Simulated Google and Apple sign people in for the tests. It answers after `latency`, so that screens wait as for a real cloud.
- **The configuration's `[cloud]`:** the simulated cloud by default; a cloud's address from `config/local.toml` or `AI_APP_CLOUD_ADDRESS`, and `http://` only in development (SEC-1).
- **A check for every definition** ([ADR-0005](../decisions/0005-checks-for-every-definition.md)), and arrays for the types of lists.
- **Tests:**
  - ai-platform's four examples replay against the simulated cloud, through its transport, as against ai-cloud;
  - the client runs end to end on it, and the fetch transport against a stand-in for fetch;
  - the rules that the examples leave out: limits, lifetimes, what deleting takes;
  - 27 mutants of the client and the simulated cloud. One survived at first: a test of a fresh sign-in's age passed because its nonce had expired too, and now isolates that rule.

**Decisions:** delegated, as in the entry before.
- ADR-0005: a check for every definition.
- The rest of the way splits in three: this step; then `account`, with the session, signing in and its screens; then `homes`.
- The client sends again only what an Idempotency-Key makes safe. TanStack Query retries the queries, and no mutation by default ([its guide](https://tanstack.com/query/latest/docs/framework/react/guides/mutations), read 2026-11-04).
- The simulated cloud asks the JavaScript engine for time zones: in Node, ICU; on a phone, the platform's own, which [Hermes's Intl](https://github.com/facebook/hermes/blob/main/doc/IntlAPIs.md) uses. ai-cloud reads tzdata's list.

**Problems / unfinished:**
- Met and solved: the builds failed in CI, where Expo reads the configuration. smol-toml makes tables without a prototype, which Expo's reader cannot serialize, and the runtime settings now carry the `[cloud]` table. The loader makes them ordinary objects, and a test reads the configuration through Expo's own `getConfig`.
- A refresh whose answer is lost ends the session: the cloud has rotated the token, and the next refresh presents the old one, which counts as stolen (RFC 9700, 4.14.2). Large providers allow a grace period for this, read 2026-11-04:
  - Okta's "grace period for token rotation": 30 seconds by default, from 0 to 60 ([guide](https://developer.okta.com/docs/guides/refresh-tokens/main/));
  - Auth0's "reuse interval": off by default, and only for the token just replaced ([docs](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation)).

  To settle in ai-platform before `account`'s session.
- Since Android 9 (API level 28), Android refuses plain HTTP unless the app's network security configuration permits it, for an address or for all ([Android's documentation](https://developer.android.com/privacy-and-security/security-config), read 2026-11-04). A developer's own cloud over `http://` needs that permission, for its address only, which comes with `account`.

**Next:** `account`: the session in secure storage, signing in with the development provider, and its screens; TanStack Query at the root.

## 2026-11-12 — Screen readers say the app's messages, on every platform

**Done:** `Notice`, in the design system: a message that appears or changes where people look for it, an `alert` for what went wrong or a `status` for news.
- **Each screen reader says it,** as it comes and as its text changes, never again for a mere render. On iOS it is announced; on Android and the web it is a live region, on the screen before its text. A new `key` says the same text again for a new event: the scanner's refusal of a second code that is refused the same way.
- **Every screen uses it:** the failures of every screen, a field's fault (`TextField`), the scanner's refusal (alerts), and the note after a demotion (a status). The lint refuses a role of `alert` or `status`, `aria-live` and `accessibilityLiveRegion` outside the design system.
- **The studio's components page** has notices to try: a failure, and the same failure again in other words; news; both at once.
- **Tests:** each platform's path, all failing on the old code. iOS announces an alert at once and a status in turn, again when the text changes or the notice comes back, never for a mere render, and two that come together one after the other. Android's and the web's regions come empty, then with their text. A field's fault, on iOS and on Android; a second code refused, said again; the demotion's note, a status; the studio's notices. `renderScreen` now wraps the screen in its providers, so that `rerender` keeps them. 23 mutants, all killed. One survived at first: a notice whose role changed, its text the same, was not said again on iOS, though Android says a region whose mode changes (`View.setAccessibilityLiveRegion`); a test now holds it.

**Decisions:** delegated. Sources read 2026-11-12.
- **iOS has no live regions:** a notice is announced (`UIAccessibility.Notification.announcement`), through React Native 0.88's `AccessibilityInfo.announceForAccessibilityWithOptions` (`AccessibilityInfo.js`, `RCTAccessibilityManager.mm`). React Native gives the `alert` and `status` roles no trait on iOS (`RCTViewManager.m`), so the role alone said nothing.
- **How urgent:** WAI-ARIA's: an alert is assertive, a status polite.
  - On iOS, an alert has the high priority, which interrupts and is not interrupted, and a status is queued behind what is being said (Apple's `UIAccessibilityPriority` and `UIAccessibilitySpeechAttributeQueueAnnouncement`). The priority exists from iOS 17, and React Native ignores it before; the app supports iOS 15.1, where an alert interrupts as an announcement does by default.
  - On Android, the live region's modes are the same two. TalkBack speaks an assertive region at once, uninterrupted by new speech, and queues a polite one (TalkBack `EventTypeWindowContentChangedFeedbackRule`, master 229212f).
- **The region first:** Android speaks a live region when a view already on the screen changes (AOSP `View.notifyViewAccessibilityStateChangedIfNeeded`, `TextView.setText`); a view that arrives with its text is not spoken by itself. So on Android and the web, a notice renders empty, then its text in a layout effect, each commit mounted apart (React Native 0.88 pushes each transaction, `enableMountingCoordinatorPullModelAndroid` being off). React Aria's announcer makes its regions first for the same reason (`LiveAnnouncer.tsx`, main d354aa2).
- **Two at once** are both heard, in the screen's order: React Aria appends each message to its region. On iOS, the notices announced in one tick after the first are queued behind it.
- **When it is said** follows Expensify (`useAccessibilityAnnouncement`, main d29e2d9): as a message appears and as it changes, reset when it goes. React Native Paper marks its banner and snackbar polite (main 2b335aa).
- **Android's `Text` drops `aria-live`:** only React Native's `View` maps it (`View.js`), so the fault of a field and the scanner's refusal, marked `aria-live`, were silent on Android too. `Notice` sets `accessibilityLiveRegion` on Android, and `aria-live` on the web, which React Native for Web prefers.
- **No announcement on Android:** `TextField`'s old one sent `TYPE_ANNOUNCEMENT`, which Android deprecates for live regions (`AccessibilityInfoModule.kt`).

**Problems / unfinished:**
- Not heard on a phone yet: VoiceOver and TalkBack on the studio's notices and a screen's failures.
- A test file run alone still never exits; mutants' runs pass `--forceExit`.

## 2026-11-12 — Set-up's protocol client, the first step of adding a device

**Done:** the first step of `setup`, the feature that adds a robot to a home (ai-platform ADR-0013, set-up 2.0). It has no screen and no radio yet: nothing a person sees changes.
- **The protocol, in `src/setup/domain`:** the set-up string and the typed code, fragments, SPAKE2+ on P-256 (RFC 9383), the encrypted channel, and messages checked against the protocol's schema, made from ai-platform at `app/v1.3` like the app API's (set-up's schema and examples are the same at `app/v1.5`). Its errors name what failed, never a value.
- **The session, in `src/setup/services/session.ts`:** `greet` sends the hello over a `Link` (the port the radio will fill), a `Greeting` tries one code, and a `Session` lists networks, joins one, sets the device up, registers it and finishes. One answer is awaited at a time, within `[setup] answer_timeout`; a message out of turn, out of order or broken ends the session. A fragment that comes while nothing is asked ends it before the app keeps it, and a message being joined takes no more room than the length it announced, so that a device cannot make the app hold what it sends. The app ends a session by closing its link.
- **A simulated device** (`src/setup/adapters/simulated/device.ts`) plays the robot's side: its code, its networks, its refusals, a new code after each attempt, as the robot draws one, one session at a time, and a registration signed with its key.
- **`src/shared/bytes`:** base64url, read strictly, and the phone's randomness, moved from the simulated cloud.
- **Tests:** RFC 9383's vector; ai-platform's `session.json` replayed byte for byte: w0 and w1, the context, both shares, both confirmations, the keys and the first encrypted message. The whole example against the simulated device, its registration verified; a wrong code, a busy device, refused servers and joins; a fake link for each way a session is lost; a scripted device for answers out of turn. 36 mutants: 33 killed at first. Of the 3 that survived, 2 needed tests, now written: a fake link that skipped the listener of a link already ended, and a long message after the one that opens the channel, which only the `Conversation` itself can be asked. The third was code to remove: the session refused a clear message after the channel had opened, which the rule on `reply_to` refuses already. The second review ran the client against the robot's own set-up module, through a bridge: a whole set-up passed. It found three things, now fixed, each with a test that failed before: continuations without data that the app kept while nothing was asked, the test of UTF-8 that JSON's own failure passed, and the simulated device keeping its code when the app left during scrypt. 8 mutants of the fixes, all killed.

**Decisions:** delegated. Sources read 2026-11-12.
- **Cryptography** ([ADR-0006](../decisions/0006-set-up-cryptography.md)): noble's audited libraries in JavaScript, so that the examples replay in Jest on the code that ships; the phone's randomness through `expo-crypto`; `TextDecoder` with `fatal`, which Hermes V1 has.
- **Waiting for an answer:** 90 seconds, longer than the robot's `join_timeout` of 60 (ai-robot `config/base.toml`, `[modules.setup]`), the longest a device takes to answer.
- **Exact bytes:** the context hashes both hellos as they were sent, so the session keeps the bytes it wrote and read. The example's JSON is spaced by Python, so its messages' bytes are replayed in the units that hash them, and the whole flow runs against the simulated device.
- **Set-up's checks** are made with Ajv's `strictTypes` off: the schema's parts are objects without saying `type: object`, which JSON Schema allows.
- **An attempt costs its code,** as on the robot (ai-robot `modules/setup.py`, `_after`): the simulated device draws a new code once the app has sent its share, whenever the session ends after it. The protocol calls a failed attempt "a session that sent a `share` but did not confirm", and has the app take up an interrupted set-up "with the code shown then".
- **`busy` answers the app's `hello`,** with `reply_to`, on the simulated device. The protocol has the device count the app as connected from its first write, after the app has enabled indications (The Bluetooth service, "First, indications"), and gives an error `reply_to` when it answers a message. The robot sends `busy` as soon as an app connects, before that write and without `reply_to`: it departs from the protocol, and an indication sent before the app has enabled them can be lost. The app reads both.
- **The module's structure** follows the app's (ADR-0002): `domain`, `ports`, `services`, `adapters/simulated`, one `index.ts`; `SetupSettings` lives in `shared/config`, which may not import a module.

**Problems / unfinished:**
- scrypt's time under Hermes on a phone is not measured: the next step does.
- ai-platform could say `type: object` in set-up's schema, so that its checks need no exception: a follow-up for that repository.
- **For the next steps,** from the second review:
  - the answer's timer starts once the app's writes have settled, so the Bluetooth adapter must settle every write and every close, rejecting a write once the link has ended, or a session waits for ever;
  - the screens must send no `register` and no `configure` to a bound device, and must keep the device whose discriminator matches before they try a code;
  - the session's keys stay referenced as long as its `Session` is: the screens drop it once it ends. The session does not drop them itself when it ends, because an answer that came just before the end, such as `finished` before the device disconnects, is still decrypted after it.

## 2026-11-13 — Set-up 2.2 and the app API 1.6: JSON that every side can hold

**Done:** `platform/` moves to ai-platform's `setup/v2.2` (c6f697d), which holds the app API 1.6 (`app/v1.6`) too. The set-up client and its simulated device speak set-up 2.2, as far as no radio is needed. Nothing a person sees changes. This comes before step 3 of the plan of 2026-11-12; step 2, the Bluetooth LE link, still waits for the owner's phone and the robot's Pi.
- **JSON that every side can hold** (ai-platform ADR-0014): one reader, `readJson` in `src/shared/protocols/json.ts`, for every protocol. It refuses a U+0000 or a lone surrogate in a name or a string, nesting deeper than 64 levels, the outermost counted, and a number past a double, as a text it cannot read. The nesting is counted before the text is parsed, as ai-robot's `read_json` does, so that the answer depends on the text. The app API's client takes such an answer as one it cannot read (`ProtocolError`); the simulated cloud answers such a body with `400`, which replaces its own check of lone surrogates; set-up refuses such a message as one it cannot read.
- **Fragments** hold the ATT MTU minus 3 bytes, and never more than 512: `split` caps the room a link gives, so that every link, and the simulated device, keep to it.
- **The simulated device keeps matching the robot** (ai-robot main 283ef2c, `modules/setup.py` and `core/setup_session.py`, which speak 2.1 with 2.2's rules):
  - an error replies to the message it is about whenever its `seq` can be read, a message that breaks the schema included; one that cannot be decrypted, or read, gets none, sealed once the exchange is done, where the device used to close without a word;
  - `busy` answers a second app's `hello`, with `reply_to` 1, whatever version it speaks;
  - names are bytes: `ssid` when they are UTF-8 without a NUL byte, `ssid_hex` otherwise, in `networks`, `joined` and `info`; a `join` matches by bytes, by either field, and a name of more than 32 bytes gets `protocol`;
  - `networks` leaves out hidden networks, a scan's name of no bytes, of NUL bytes alone or of one space (NetworkManager's `_nm_utils_is_empty_ssid_arr`, as the robot reads it), and names too long, and gives at most 50.
- **Set-up's checks** are made with Ajv's `strictTypes` on, now that the schema's objects say `"type": "object"`: `scripts/protocols.mjs` has no exception per protocol any more.
- **Tests:** the reader on its own (depth at 64 and 65, brackets and escapes within strings, each kind of unholdable string, numbers past a double); fragments over a link of 514 bytes, both ways; the device's `reply_to`, `busy`, names and hidden networks; the cloud's answers and the simulated cloud's bodies. 28 mutants: 25 killed at first. Of the 3 that survived, 2 needed tests, now written: an escaped quote before brackets within a string, and a network name that begins with the bytes of a byte order mark. The third was code to remove: the device's own check of a readable `seq`, which the schema already refuses; its error now takes `seqOf` whatever the schema found.

**Decisions:** delegated.
- **The app says `"2.2"`** in its `hello`, and so does the simulated device: each side gives the version it speaks, and only the major one decides (set-up's Versions). The robot says `"2.1"`.
- **A number past a double is refused,** which ADR-0014 allows and the robot does: JSON.parse would read it as an infinity, which no schema bound catches.
- **A byte order mark is kept, and so refused:** RFC 8259 (8.1) lets a reader ignore one, but no side sends one, and the robot refuses one. `TextDecoder` drops it unless told `ignoreBOM`.
- **The cap is the protocol's, not the link's:** the `Link` port still gives the ATT MTU minus 3, which can exceed 512 (Android 14 asks for 517), and `split` takes the smaller.
- **The app still ends a session by closing its link,** without sending an error: the protocol lets either side end it on a message it cannot read.

**Problems / unfinished:**
- No screen offers "Other network…" for a hidden network yet: whether the app offers it waits for the owner. The client already sends `join` with `hidden` and `security`.
- The robot sends `busy` to every app until ai-robot#45 lands (BlueZ's indications); the simulated device sends it to the second app only, as the protocol says.

**Next:** step 2, the Bluetooth LE link, once the phone and the Pi are at hand; otherwise step 3, the app API's devices, at `app/v1.6`.

## 2026-11-13 — The app API's devices

**Done:** step 3 of the plan of 2026-11-12, at the app API 1.6 (`app/v1.6`): the app's part of adding a device, as far as the cloud goes. It has no screen: nothing a person sees changes.
- **The client, in `src/shared/cloud/client.ts`:**
  - `devices`, a page of a home's devices, and `device`;
  - `createDeviceChallenge`, then `registerDevice`, with an Idempotency-Key. It answers `Registered`: the device, and `added`, true for a device new to the home (`201`), false for one the home held already (`200`), such as a device that lost what it kept;
  - `updateDevice`, which renames with `If-Match`, sending the ETag exactly as it was received (ADR-0013); a stale one comes back as `Refused.stale`;
  - `removeDevice`, which only unlinks the device (PROV-4).
- **The simulated cloud** (`adapters/simulated/devices.ts`, `registration.ts`) does what ai-cloud does (main 8362bcd, `devices/routes.py` and `service/devices.py`), in the same order:
  - the challenges' rate for each account; the home; the answer kept with the Idempotency-Key; the role;
  - the challenge the registration names, which must be this home's and this account's, and not expired; then the registration itself;
  - the challenge is used before the outcome, and the outcome is kept with the key whatever it is, a refusal included.
- **A registration is verified as ai-cloud's domain does:** its `typ`; a public P-256 key, its coordinates read canonically; ES256, with either `s`; the claims, the audience, and `iss` and `sub` the same identifier. The device's key is its thumbprint (RFC 7638).
  - A device whose id or key another home holds is `device_taken`; a home that is full refuses a new one with `device_limit_reached`.
  - A person who leaves loses their challenges, a home deleted loses its devices, and a device removed loses the answers kept for it.
  - `connectDevice` and `disconnectDevice` play the device's own side: its control channel, opened with the key it registered, and what its hello says it is.
- **Tests:**
  - `devices.json` replayed against the simulated cloud, its robot connecting where the example says it does;
  - the example's six registrations verified on their own, to the thumbprint it names;
  - each way a registration is refused, with its retry, which gets the same answer, and its challenge, used;
  - the rate, the roles, a stranger, a device taken, the limit, the names, renaming with `If-Match`, removing, a person who leaves, a home deleted, and pages;
  - the client, end to end.
  - The simulated cloud's harness moved to `tests/shared/cloud/simulated.ts`, and a robot of the tests' own (`robot.ts`) signs registrations with its key.
  - 50 mutants, all killed: 43 at first, and 7 of the guards that only the registration's own tests reach, written after.
- **The review found one bug.** A header that is no UTF-8 made the simulated cloud throw under Jest instead of refusing it, because `TextDecoder`'s error there is of another realm's class. The call is now caught alone, as `readMessage` does, and the checklist says so.

**Decisions:** delegated. Sources read 2026-11-13.
- **The client's methods** follow the app API's operations. `registerDevice` answers `added` from the status alone, so that a screen can say whether the device is new to the home.
- **The simulated cloud's address** is `https://simulated.invalid`: a name under `.invalid` never resolves (RFC 6761, 6.4). The replay of `devices.json` uses the example's own, `https://cloud.example`.
- **The simulated cloud's settings** are the protocol's (the app API's Settings): a challenge lives 300 seconds, a home holds 300 devices, and an account gets 10 challenges a minute.
- **Either `s` verifies:** noble refuses a high `s` unless told (`lowS: false`); JWS sets no rule on it (RFC 7518, 3.4).
- **A byte order mark at the start of a registration's part is dropped,** as ai-cloud's PyJWT reads a part with Python's `json.loads`, which takes one (`json.detect_encoding`). Set-up, which the robot reads with no such library, refuses one (the entry above).
- **A key's coordinates are read canonically,** as ai-cloud's `b64url_decode` reads them: base64url with other unused bits would give one key two thumbprints.
- **A challenge is asked without an Idempotency-Key,** as the app API defines it, and is not retried: a lost one costs one challenge of the rate, and the next attempt asks again.

**Problems / unfinished:** none.

**Next:** step 2, the Bluetooth LE link, once the phone and the Pi are at hand; otherwise step 4, the flow's screens.

## 2026-11-13 — The home's devices

**Done:** step 5 of the plan of 2026-11-12, before step 4, whose screens wait on the owner's choice of a row for a network that hides its name. What a person sees:
- **The home's screen lists its devices,** above its people: each by its name, and whether it is online or offline. A home without one says so.
  - A device without a name, which a cloud of 1.4 registered, goes by the app's name for its kind: "Robot", or "Device" for a kind the app does not know, or before the device's first hello.
- **Each device has its page** (`/homes/[id]/devices/[deviceId]`), under its name:
  - whether it is online;
  - what it is, its model and its software, once it has said;
  - the day it joined the home. Two devices may share a name, and their pages tell them apart.
- **The owner and admins rename it,** with `If-Match` (ADR-0013), to a name of 1 to 100 characters.
  - A name changed meanwhile is said so, and what the person typed stays, to save again.
  - A member is offered neither renaming nor removing. A role taken away while the page is open is said so.
- **Removing it** is a danger button, confirmed in the phone's dialog, which says what stays (PROV-4):
  - the device leaves the home, and can be set up again;
  - it keeps its Wi-Fi network, its name and its settings, and is reset to its factory settings before it goes to someone else.
  - A device removed meanwhile is no failure. The page then goes back, or, when a link opened it with nothing behind it, to the home.
- **The module `devices`** (`src/devices`) has `HomeDevices` and `DeviceScreen`. `homes` gives it `OneHome` and `mayManage`. The home's screen takes the devices as a slot that the routes fill, since `devices` reads `homes`, and the reverse would be a cycle.
- **Tests:**
  - 20 in `tests/devices/devices.test.tsx`, on the simulated cloud, with the tests' robot;
  - three routes in `tests/app.test.tsx`: the main screen leads to a device's page; a page with nothing behind it leads to the home after a removal; signed out, a device's page leads to signing in.
  - 30 mutants, all killed.
- **Writing the tests and the review found three bugs,** each fixed, and the checklist names their kinds:
  - The day a device joined showed its time too. MF2's `:datetime` formats a time whatever `dateFields` says (messageformat 4.1.0, `lib/functions/datetime.js`): a day alone is `:date`, with its `fields` and `length`.
  - A page that a link opened went back to nothing after a removal. It now goes to the home.
  - A test's `screen.unmount()` was not awaited. In React Native Testing Library 14 it is asynchronous: its `act` overlapped the next render, and the tests after it failed.
  - The kind's name, which a person may keep as the device's name, came from `useText`, which the checklist keeps from data. It showed no mark, since the kinds' names hold no value, and now comes from `usePlainText`.

**Decisions:** delegated. Sources read 2026-11-13.
- **Online and Offline,** as Google Home says of devices that do not answer: they "appear offline" (support.google.com/googlehome/answer/9243422). Apple's Home says "No Response" when a command gets none (support.apple.com/en-us/102056), which is not what the control channel's state says.
- **Removing is at the bottom of the device's page, and confirmed first:**
  - Apple's "Remove Accessory" is at the bottom of its settings (support.apple.com/en-us/102056);
  - Google's "Remove [product name]" is confirmed when prompted (support.google.com/googlehome/answer/9293132);
  - both then tell the person to reset the device as its maker says, which the dialog does.
- **The dialog names no way to reset the robot:** ai-robot (main 283ef2c) has none yet. Its ADR-0014 defines one, which wipes the data partition and clears the TPM, and ADR-0016's follow-up puts it in the panel. The dialog names it once it exists.
- **The devices' query is under the home's key** (`['homes', id, 'devices']`), so that leaving a home forgets them with it.
- **A device is renamed only with its ETag.** A cloud of 1.4 sends none, and renames nothing: the page then shows the name as a title.
- **A device without a name goes by its kind's name** (the app API 1.6, Naming a device), which is also the name that renaming starts from.
- **The devices are read again after a change, whatever the answer.** A removal answered 404 is a device removed meanwhile, which is what removing wanted, as for revoking an invitation.
- **A renamed device goes into the cache at once,** so the home's list has its new name while the devices are read again.

**Problems / unfinished:**
- The person's page goes back after removing someone, and a page that a link opened has nothing to go back to. The same fix belongs there, in a change of its own.
- The header's title is native, which Jest does not draw, so the device's name as its title is not tested.
