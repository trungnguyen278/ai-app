## 2026-11-04 — The app API's client, and the simulated cloud

**Done:** `shared/cloud`, ADR-0004's second step.
- **The client**, over a transport that is a port:
  - `SignInClient` asks for nonces, exchanges ID tokens, refreshes, signs out, and asks the development provider for ID tokens;
  - `CloudClient` reaches the account, its sessions, homes, their people and invitations;
  - it sends the access token, renews it once on 401 through `Credentials`, which `account`'s session will be, sends `If-Match` and walks pages;
  - each refusal becomes an error that names the operation and what happened, never a value;
  - a request with an Idempotency-Key is sent again with that key when no answer came, or when its first copy still runs (409), up to `retries` times, each wait twice the last.
- **The fetch transport:** a time limit, a limit on an answer's size (SEC-15), and no cookies.
- **The simulated cloud:** the app API 1.2 in memory, as ai-cloud serves it, with its checks in its order and its settings' values. Simulated Google and Apple sign people in for the tests. It answers after `latency`, so that screens wait as for a real cloud.
- **The configuration's `[cloud]`:** the simulated cloud by default; a cloud's address from `config/local.toml` or `AI_APP_CLOUD_ADDRESS`, and `http://` only in development (SEC-1).
- **A check for every definition** ([ADR-0005](../decisions/0005-checks-for-every-definition.md)), and arrays for the types of lists.
- **Tests:**
  - ai-platform's four examples replay against the simulated cloud, through its transport, as against ai-cloud;
  - the client runs end to end on it, and the fetch transport against a stand-in for fetch;
  - the rules that the examples leave out: limits, lifetimes, what deleting takes;
  - 27 mutants of the client and the simulated cloud. One survived at first: a test of a fresh sign-in's age passed because its nonce had expired too, and now isolates that rule.

**Decisions:** delegated, as in the entry before.
- ADR-0005: a check for every definition.
- The rest of the way splits in three: this step; then `account`, with the session, signing in and its screens; then `homes`.
- The client sends again only what an Idempotency-Key makes safe. TanStack Query retries the queries, and no mutation by default ([its guide](https://tanstack.com/query/latest/docs/framework/react/guides/mutations), read 2026-11-04).
- The simulated cloud asks the JavaScript engine for time zones: in Node, ICU; on a phone, the platform's own, which [Hermes's Intl](https://github.com/facebook/hermes/blob/main/doc/IntlAPIs.md) uses. ai-cloud reads tzdata's list.

**Problems / unfinished:**
- Met and solved: the builds failed in CI, where Expo reads the configuration. smol-toml makes tables without a prototype, which Expo's reader cannot serialize, and the runtime settings now carry the `[cloud]` table. The loader makes them ordinary objects, and a test reads the configuration through Expo's own `getConfig`.
- A refresh whose answer is lost ends the session: the cloud has rotated the token, and the next refresh presents the old one, which counts as stolen (RFC 9700, 4.14.2). Large providers allow a grace period for this, read 2026-11-04:
  - Okta's "grace period for token rotation": 30 seconds by default, from 0 to 60 ([guide](https://developer.okta.com/docs/guides/refresh-tokens/main/));
  - Auth0's "reuse interval": off by default, and only for the token just replaced ([docs](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation)).

  To settle in ai-platform before `account`'s session.
- Since Android 9 (API level 28), Android refuses plain HTTP unless the app's network security configuration permits it, for an address or for all ([Android's documentation](https://developer.android.com/privacy-and-security/security-config), read 2026-11-04). A developer's own cloud over `http://` needs that permission, for its address only, which comes with `account`.

## 2026-11-12 — Screen readers say the app's messages, on every platform

**Done:** `Notice`, in the design system: a message that appears or changes where people look for it, an `alert` for what went wrong or a `status` for news.
- **Each screen reader says it,** as it comes and as its text changes, never again for a mere render. On iOS it is announced; on Android and the web it is a live region, on the screen before its text. A new `key` says the same text again for a new event: the scanner's refusal of a second code that is refused the same way.
- **Every screen uses it:** the failures of every screen, a field's fault (`TextField`), the scanner's refusal (alerts), and the note after a demotion (a status). The lint refuses a role of `alert` or `status`, `aria-live` and `accessibilityLiveRegion` outside the design system.
- **The studio's components page** has notices to try: a failure, and the same failure again in other words; news; both at once.
- **Tests:** each platform's path, all failing on the old code. iOS announces an alert at once and a status in turn, again when the text changes or the notice comes back, never for a mere render, and two that come together one after the other. Android's and the web's regions come empty, then with their text. A field's fault, on iOS and on Android; a second code refused, said again; the demotion's note, a status; the studio's notices. `renderScreen` now wraps the screen in its providers, so that `rerender` keeps them. 23 mutants, all killed. One survived at first: a notice whose role changed, its text the same, was not said again on iOS, though Android says a region whose mode changes (`View.setAccessibilityLiveRegion`); a test now holds it.

**Decisions:** delegated. Sources read 2026-11-12.
- **iOS has no live regions:** a notice is announced (`UIAccessibility.Notification.announcement`), through React Native 0.88's `AccessibilityInfo.announceForAccessibilityWithOptions` (`AccessibilityInfo.js`, `RCTAccessibilityManager.mm`). React Native gives the `alert` and `status` roles no trait on iOS (`RCTViewManager.m`), so the role alone said nothing.
- **How urgent:** WAI-ARIA's: an alert is assertive, a status polite.
  - On iOS, an alert has the high priority, which interrupts and is not interrupted, and a status is queued behind what is being said (Apple's `UIAccessibilityPriority` and `UIAccessibilitySpeechAttributeQueueAnnouncement`). The priority exists from iOS 17, and React Native ignores it before; the app supports iOS 15.1, where an alert interrupts as an announcement does by default.
  - On Android, the live region's modes are the same two. TalkBack speaks an assertive region at once, uninterrupted by new speech, and queues a polite one (TalkBack `EventTypeWindowContentChangedFeedbackRule`, master 229212f).
- **The region first:** Android speaks a live region when a view already on the screen changes (AOSP `View.notifyViewAccessibilityStateChangedIfNeeded`, `TextView.setText`); a view that arrives with its text is not spoken by itself. So on Android and the web, a notice renders empty, then its text in a layout effect, each commit mounted apart (React Native 0.88 pushes each transaction, `enableMountingCoordinatorPullModelAndroid` being off). React Aria's announcer makes its regions first for the same reason (`LiveAnnouncer.tsx`, main d354aa2).
- **Two at once** are both heard, in the screen's order: React Aria appends each message to its region. On iOS, the notices announced in one tick after the first are queued behind it.
- **When it is said** follows Expensify (`useAccessibilityAnnouncement`, main d29e2d9): as a message appears and as it changes, reset when it goes. React Native Paper marks its banner and snackbar polite (main 2b335aa).
- **Android's `Text` drops `aria-live`:** only React Native's `View` maps it (`View.js`), so the fault of a field and the scanner's refusal, marked `aria-live`, were silent on Android too. `Notice` sets `accessibilityLiveRegion` on Android, and `aria-live` on the web, which React Native for Web prefers.
- **No announcement on Android:** `TextField`'s old one sent `TYPE_ANNOUNCEMENT`, which Android deprecates for live regions (`AccessibilityInfoModule.kt`).

**Problems / unfinished:**
- Not heard on a phone yet: VoiceOver and TalkBack on the studio's notices and a screen's failures.
- A test file run alone still never exits; mutants' runs pass `--forceExit`.

## 2026-11-12 — Set-up's protocol client, the first step of adding a device

**Done:** the first step of `setup`, the feature that adds a robot to a home (ai-platform ADR-0013, set-up 2.0). It has no screen and no radio yet: nothing a person sees changes.
- **The protocol, in `src/setup/domain`:** the set-up string and the typed code, fragments, SPAKE2+ on P-256 (RFC 9383), the encrypted channel, and messages checked against the protocol's schema, made from ai-platform at `app/v1.3` like the app API's (set-up's schema and examples are the same at `app/v1.5`). Its errors name what failed, never a value.
- **The session, in `src/setup/services/session.ts`:** `greet` sends the hello over a `Link` (the port the radio will fill), a `Greeting` tries one code, and a `Session` lists networks, joins one, sets the device up, registers it and finishes. One answer is awaited at a time, within `[setup] answer_timeout`; a message out of turn, out of order or broken ends the session. A fragment that comes while nothing is asked ends it before the app keeps it, and a message being joined takes no more room than the length it announced, so that a device cannot make the app hold what it sends. The app ends a session by closing its link.
- **A simulated device** (`src/setup/adapters/simulated/device.ts`) plays the robot's side: its code, its networks, its refusals, a new code after each attempt, as the robot draws one, one session at a time, and a registration signed with its key.
- **`src/shared/bytes`:** base64url, read strictly, and the phone's randomness, moved from the simulated cloud.
- **Tests:** RFC 9383's vector; ai-platform's `session.json` replayed byte for byte: w0 and w1, the context, both shares, both confirmations, the keys and the first encrypted message. The whole example against the simulated device, its registration verified; a wrong code, a busy device, refused servers and joins; a fake link for each way a session is lost; a scripted device for answers out of turn. 36 mutants: 33 killed at first. - **The path names the robot's labels in English, in both catalogs,** as the robot's screen shows them: its texts are English, and their translation is made where they are (ai-robot ADR-0016, its consequences; ADR-0023, decision 1; the long press, ADR-0016, decision 4). When the robot's labels change, or are translated, these texts follow.

## 2026-11-20 — `readJson` against ADR-0014's traps

**Done:** `readJson` checked against the four traps that ai-cloud and ai-robot met with ADR-0014 (ai-platform), each tested. Nobody sees a change, except that a text holding a name twice in one object is now refused.
- **A repeated name** was taken, and `JSON.parse` kept its last value: a U+0000 or a number past a double in the value it dropped passed unseen, where ai-robot (`core/data.py`, at 0c8e551) and ai-cloud (`shared/protocols.py`, at 32bddd9) refuse the text. `readJson` now refuses it, with "repeats a name in an object", after `JSON.parse` has taken the text as JSON.
- **The depth count** was already linear: it reads each string once, passing over each escape, as the robot's pattern `"[^"\\]*(?:\\.[^"\\]*)*"?` does, and before the text is parsed. Tests now time it, with the new pass, on eight shapes of text up to 1 MiB.
- **An integer past a double,** such as a 1 followed by 400 zeros, was already refused as `1e400` is: `JSON.parse` reads both as an infinity. Tests now hold both spellings.
- **`uniqueItems`**: Ajv's generated checks compare every pair of items when the items' schema is a `$ref`, as `languages` is, which takes time in the square of the list's length. They check `maxItems` first and stop at the first error, so a long list is refused before its items are compared. A test now holds that, for the app's two lists and set-up's one, up to 65,536 items.
- Tests: 10 more. 23 mutants, 20 of `readJson` and 3 of the generated checks: all killed.

**Decisions:** delegated. Sources read 2026-11-20.
- **Repeated names are refused,** which ADR-0014 lets a receiver do (decision 4) and I-JSON forbids (RFC 7493, 2.3), so that the app refuses what the other sides refuse. ADR-0014 did not require it, since `JSON.parse` keeps no repeated names and the app would need a parser of its own. A second pass over the text finds the names instead: it follows strings and brackets, as the depth count does, and decodes each name with `JSON.parse`, so that an escaped name is the same name. It runs only on a text that is JSON, so a text that is not is refused as such, whatever its names.
- **The time tests grow the text, from 16 KiB to 1 MiB,** with a budget for each size of 0.1 s and 4 ms a KiB, room for a runner several times slower than this machine. Jest cannot stop synchronous code at its timeout, so a reader that took the square of the length would hang a test of 1 MiB alone. With growing sizes, it fails at a small one. At 1 MiB, the slowest shape, many small objects, took about 0.5 s here, against a budget of 4.2 s.
- **`uniqueItems` is left to Ajv** (8.20.0, `lib/vocabularies/validation/uniqueItems.ts`): `scripts/protocols.mjs` generates the checks without `allErrors`, and in them `maxItems` comes before `uniqueItems`, so it guards the comparison. The test fails if a later generation changes either.

## 2026-11-21 — Adding a device: the Bluetooth LE link

**Done:** step 2 of the plan of 2026-11-12. Set-up's radio port speaks Bluetooth LE, through react-native-ble-manager ([ADR-0007](../decisions/0007-bluetooth-le-library.md)), tried on an Android phone against the robot's set-up module on the Pi. In a development or store build, "Add device" finds a real robot; Expo Go and the web still say that set-up is not supported there.
- **`adapters/bluetooth/radio.ts`:** `BluetoothRadio` scans for the set-up service, connects, learns the size of a write and turns Answer's indications on before the first write, all within `[setup].connect_timeout`, else lets the device go. Its link writes one fragment per write, with a response, refuses one longer than a write, hears its own device's Answer only, and ends when the device disconnects: a write waiting then rejects. A write that the device does not confirm within `[setup].write_timeout` ends the link.
- **`adapters/bluetooth/phone.ts`:** the library's `Central`: Android's runtime permissions by its API level, a scan in the foreground's mode, the MTU that Android asks for, an iPhone's length of a write without a response, and an iPhone's state once its central has started. Before Android 12, the Location setting, read by the app's own Expo module `modules/location-setting`.
- **The build:** the library's config plugin, with `neverForLocation`, and the iPhone's reason from the catalogs (`native.bluetooth`). `[setup].radio = "bluetooth"` picks it, as in `base.toml`; the development environment keeps the simulated radio.
- **On the phone,** an Android 17 phone in a debug build, against ai-robot's set-up module at 0c8e551 on the Pi, its network simulated:
  - The scan for the service found the robot, and connecting took about a second. The MTU asked, 515, came back as 517, so writes of 514 bytes, each passed to the library as its `maxByteSize`. The descriptor's write was confirmed before the first write. A session's nine writes, of 42 to 141 bytes, went as one write each.
  - A whole session: `hello`, SPAKE2+ with the code the robot showed, the networks, `join`, the settings and the registration, which the robot signed before it closed set-up. The app then named the device, which its home lists as offline: the app's cloud is simulated, and so is the robot's, which never sees the app's. The robot's simulated cloud reports it bound, which ends the flow at "taken", as it should: the whole session used a launcher, in a tree of its own on the Pi, that reports it unbound.
  - The failures: a wrong code (the code step's notice; the robot counted the attempt); the robot's Bluetooth turned off mid-session (the phone heard the disconnection, and the next step said "interrupted"); the phone's Bluetooth off before set-up (the radio step, then a retry worked) and during it ("interrupted"); the permission refused for good (the settings step, whose button opens the app's details; once it was granted, back to the code step).
  - scrypt, ADR-0006's follow-up: 50.5 to 52.9 seconds in five sessions; the rest of SPAKE2+ took about 0.1 s.
- Tests: 58 more, over a stand-in for the library and a fake central before the simulated device; the configuration's test checks the plugin and the reason. 76 mutants of the adapters and the configuration: all killed, once the review had added what eight survivors showed missing (a connection that takes its time within `connect_timeout`, its timer cleared, a failure to let a device go, no write once the link has ended, the radio's own `allow`) and taken out a `clear` that nothing could observe. The second review's five findings brought 13 of the tests, and 28 mutants of their fixes, the reviewer's three survivors of `phoneCentral` among them: all killed, once a test had closed the flow while it read Bluetooth's state after an empty scan.

**Decisions:** delegated. Sources read 2026-11-21.
- **react-native-ble-manager 13.0.1,** not the 13.0.0 planned: released 2026-11-14, with a fix to Android's scan (#1456).
- **The size of a write.** Android asks for 515, a fragment of 512 and the ATT's 3 bytes, and takes the MTU agreed less 3: from Android 14 it asks for 517 whatever the app asks, and the device answers with its own (Android 14's behaviour changes). An iPhone settles its MTU itself, and the size is the length of a write without a response, the ATT MTU less 3: a write with a response may be longer only as a long write, which the protocol does not use (Apple, `CBCharacteristicWriteType`). This corrects the research of 2026-11-12, which named the length of a write with a response. 20 bytes at least.
- **`connect_timeout` is 20 seconds,** as Matter's Linux central waits (connectedhomeip, `src/platform/Linux/BLEManagerImpl.cpp`, `kConnectTimeout`): an iPhone's connection does not time out on its own (Apple, `connect(_:options:)`).
- **A scan in Android's low-latency mode,** which Android recommends in the foreground only (`ScanSettings.SCAN_MODE_LOW_LATENCY`): set-up scans for a few seconds while the person waits. The library's default is the lowest.
- **Android's permissions:** from API 31, `BLUETOOTH_SCAN`, declared as never used for the location, and `BLUETOOTH_CONNECT`; before, `ACCESS_FINE_LOCATION`, which the plugin declares up to API 30 only (Bluetooth permissions). A refusal is `ask`, a refusal for good `blocked`.
- **An iPhone's state** is `ask` until its central has started, since starting it asks the person the first time; allowing starts it, without the library's alert, and waits for a state that is known.
- **The library loads once its native module is found** (`TurboModuleRegistry.get`): it throws as it loads without it, on the web, in Expo Go and in Jest.
- **Every wait ends by the app's own timer.** Connecting, the MTU and the indications race `connect_timeout` and the link's end; a write races the link's end and `write_timeout`, 35 seconds, after which the link ends. The stack's own end of a link is not enough: an ATT transaction without an answer fails after 30 seconds (Bluetooth Core, Vol 3, Part F, 3.3.3), and Android's stack then disconnects (`system/stack/gatt/gatt_utils.cc`, `gatt_rsp_timeout`), but the library never settles an Android write that the device refused for its authentication (below). 35 is the ATT's 30 and 5 seconds for the end of the link to reach the app. An iPhone's stack was not read.
- **Location before Android 12.** Until Android 11 the Bluetooth stack drops every result of a scan while Location is off (AOSP `packages/apps/Bluetooth`, `GattService.hasScanResultPermission`: `Utils.blockedByLocationOff` in `android11-release`, the secure setting `LOCATION_MODE` with `strict_location_check` on in `pie-release`), and the app runs from Android 7. The radio's new state `location` says so, with a button to Android's location settings (`Settings.ACTION_LOCATION_SOURCE_SETTINGS`, declared in the module's `<queries>` for Android 11's package visibility, and its absence on a phone caught) and a retry, as Nordic's scanner does (`Android-Common-Libraries`, `scanner-ble`, `ScanEmptyView`). The setting is read by the app's own Expo module, `modules/location-setting`, one Kotlin function that reads it as the stack does: expo-location would declare the location's permissions on every Android (its manifest), and react-native-device-info is a whole library for one function. Recorded in ADR-0007.
- **Bluetooth turned off while the flow looks for the device** shows the radio step, the code kept, rather than "no device" or, for a QR code, "expired": the flow reads the radio's state when the scan is empty and when no device was the code's.
- **Indications before the first write:** the library settles `startNotification` once the device has confirmed the descriptor's write (`Peripheral.java`'s `onDescriptorWrite`; on iOS, `didUpdateNotificationStateFor`), which the phone showed.

**Problems / unfinished:**
- **scrypt takes about 51 seconds on the phone,** in a debug build: far too long for a person waiting. ADR-0006 names the next choice, a native scrypt behind the same function, checked against the same examples. A release build was not measured.
- **No text of the app is formatted on a phone.** messageformat 4.1.0 builds an `Intl.Locale` for every message (`lib/messageformat.js`), which Hermes does not have (its `doc/IntlAPIs.md`): `src/shared/catalog/phone.ts` warns that the message "did not format" and shows its id. Jest, on Node, passes. It needs a pull request of its own, before anything else a person sees.
- **A device lost while the flow waits for the person,** at the networks for one, is told at the next step only: the session ends silently while it is idle, as step 4 designed it.
- **A single refusal of the permission** shows the settings step, as step 4 designed it, where Android would ask again. It could not be tried on this phone: React Native's debug-only local network permission, in the same "Nearby devices" group, came back granted, and Bluetooth's with it. The unit tests cover it.
- **GATT status 133,** once, right after the app was killed mid-session: the connection failed, the flow said that no device was found, and a retry worked. The app does not retry by itself.
- **The library never settles an Android write refused for authentication.** The pull request's review found it in the library's source: `Peripheral.java`'s `onCharacteristicWrite` returns before its callback for status 5 or 137, and its command queue stays busy; any device that advertises the set-up service could hold the flow at "connecting" until it disconnected. `write_timeout` ends the link, whose `disconnect` fails the callbacks waiting and empties the queue. A report upstream, for the owner to approve before it is filed:

  > **Android: `write()` never settles when the device refuses the write for its authentication (status 5 or 137), and later commands wait for ever**
  >
  > react-native-ble-manager 13.0.1, Android. A write with a response to a characteristic whose write the device refuses with Insufficient Authentication (5), or that ends in `GATT_AUTH_FAIL` (137), neither resolves nor rejects, and every later command on that device waits until `disconnect()`.
  >
  > `Peripheral.java`'s `onCharacteristicWrite` returns early for these two statuses ("*not* doing completedCommand()"): the write's callback is never called, and the command queue stays busy. Android has retried the write with authentication by then, without and then with MITM protection, and passes the status to the app only once those retries failed (AOSP `BluetoothGatt.java` in `android11-release`, `onCharacteristicWrite`, `mAuthRetryState`), so no other callback follows. Reads and descriptor reads already reject on the same statuses.
  >
  > Expected: the write rejects with its status, and the queue goes on (`completedCommand()`), as for any other status.
  >
  > To reproduce: a peripheral whose characteristic needs an authenticated write (with BlueZ, the flag `encrypt-authenticated-write`), pairing refused; `BleManager.write(...)` on it.
  >
  > Workaround: a timer in the app, then `disconnect()`, which fails the callbacks waiting (`errorAndClearAllCallbacks`) and resets the queue.
- **The library's plugin declares `BLUETOOTH` and `BLUETOOTH_ADMIN` on every Android,** where its own manifest limits them to API 30: install-time permissions, which ask nothing. A fix upstream is the owner's call.
- Not tried: Android 11 and earlier, and with them the Location module, which only compiled; an iPhone, since there is none here (ADR-0001). The robot logged no end of its session when its Bluetooth went off: on the robot's side, not looked into.
